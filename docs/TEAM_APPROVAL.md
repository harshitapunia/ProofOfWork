# Devnet MVP approval record

**Status: approved for Devnet MVP implementation by Harshita and Palak.** The [contract specification](CONTRACT_SPEC.md) and the ownership below are the agreed baseline. Ganga owns frontend integration against the reviewed interfaces.

**Accepted limits.** One submission per milestone. The MVP has no dispute-resolution mechanism or automatic payout on verifier silence. Timely unverified submissions may remain locked indefinitely. The prototype uses non-monetary DEMO tokens exclusively on Solana Devnet.

**Deployment configuration outstanding.** The [shared foundation](SHARED_FOUNDATION.md) records the configured Devnet program ID. The team-approved classic SPL Devnet DEMO mint is `GoXZxB3gErYYQ3UPKghpTwNPkcqWH1qoNbyU2VTD8Bty` (6 decimals, no freeze authority, mint authority `249mMS9awYGUyMe22zabsSCo8cH4RDo3MeN3mAHFdy69`). Deployment and upgrade authority configuration remain outstanding. Design approval permits implementation against the specification. Deployment and key generation require separate authorization.

| Area | Approved baseline or outstanding configuration | Risks and alternatives | Implementation impact |
|---|---|---|---|
| Account ABI and PDAs | Use the exact four layouts, field order, byte sizes, role bindings, enum order, seed encodings, canonical bumps and scoped client IDs. One immutable submission and completion per milestone. | A counter PDA adds state and contention. Multiple submissions need versioned seeds, a defined active submission and extra replay rules. Stable ABI changes need migration. | Freeze layouts, seed vectors and shared serializers before parallel work. |
| Program and Devnet mint identities | The Devnet program ID and single classic non-native DEMO mint above are chosen. Identify who controls program upgrades and deployment. | Single mint is intentionally restrictive. Mint allowlists, Token-2022, and mutable config require additional authority and accounting. Upgrade authority can change guarantees. | Keep token configuration and deployment gated on the remaining inputs and required authorization. Keep signing material outside Git and frontend. |
| Role enrollment and student consent | Use an immutable sponsor wallet and predesignated independent verifier, with off-chain sponsor vetting and student consent before assignment. Student signature gates evidence submission. | Key compromise, lost keys, collusion, and unwanted assignments are possible. An on-chain student co-signature or a verifier registry would add constraints and UX steps. | Document who vouches for sponsor and verifier independence and how public keys map to off-chain accounts. |
| Funding and deadlines | Require full funding before assignment, fixed absolute UTC cutoffs with an exclusive submission deadline, and one student assignment. | An expired unassigned funded milestone waits until the submission cutoff. Absolute deadlines can leave little working time. Relative windows or minimum durations require different terms and boundary tests. | Implement the specified cutoff semantics and reflect them in the UI. |
| Escrow accounting and custody | Use dedicated vault and authority PDAs, sponsor-funded rent, exact raw-unit principal, surplus returned to sponsor, canonical ATAs supplied by callers, and zero-balance vault closure in terminal instructions. | Pre-existing ATAs are required and creation costs rent. Third-party transfers can create surplus. Retaining empty vaults or creating ATAs inside settlement changes cost, accounts and scope. | Palak owns settlement and refunds, the shared escrow and checked CPI helpers, and financial security tests. Ganga must handle missing ATAs and explain rent. |
| Settlement and refund policy | Use permissionless settlement after authorized verification, caller-funded completion rent, and sponsor-only refund at or after the submission cutoff only when no submission exists. No second sponsor signature. | A sponsor may never invoke refund. A relayer can trigger settlement, but some caller must pay. Permissionless refunds or subsidies change the caller and payer model. | Implement the specified instruction accounts and validate both terminal paths, replay protection, atomicity and rent destinations. |
| Pending, invalid, and disputed work | Keep timely submissions locked until successful attestation. No rejection, resubmission, sponsor override or automatic timeout payout in this MVP. | Invalid work, verifier refusal, outages, or lost verifier keys can leave escrow locked indefinitely. A dispute resolution, verifier rotation or adjudicated refund path needs explicit protections and separate approval. | The demo accepts this limitation. Make the pending state visible in UI. Any recovery mechanism is a future design change. |
| Verification evidence and signer | Use domain-separated commitments, exact requirements manifest schema, repository and contributor ID binding, pinned commit and tests, nonce handling, isolated runner, and separate attestation signer. | A passing test only proves the agreed checks. Compromised verifiers can attest falsely, and private evidence can leak if runner controls are weak. Detached signed attestations or multiple verifiers increase replay and key management complexity. | Harshita needs a commitment fixture shared with the client, an authenticated contributor provenance rule and isolated-runner acceptance tests. |
| Completion and future reputation | Keep one immutable record per settled milestone with student, sponsor and verification provenance. Treat future eligibility policy as a consumer decision. | One record cannot prove universal skill or employment. Scores and transferable credentials add abuse and privacy risks. | Implement the approved record layout and use accurate UI wording. Defer reputation scoring and NFT/token extension design. |
| Shared interfaces and ownership | Use all eight approved instruction signatures and signer sets and the team ownership below. Establish error ordering, vault CPI helper API, and test fixtures in the shared foundation. | Independent edits to shared files can change the IDL or break settlement/refund consistency. | Assign an editor for each shared change. Keep finance and verification handlers on separate branches and jointly review any public interface changes. |

Implementation sequence:

1. Palak and Harshita land the shared Rust/Anchor foundation against the approved ABI, seeds, and state machine, with shared errors, CPI helper interfaces, and cross-language fixtures. Track deployment identities separately.
2. Under the revised split approved by both developers, Harshita implements `create_internship`, `create_milestone`, `fund_milestone`, creation/funding tests and the finance TypeScript client. Palak implements `settle_milestone`, `refund_unclaimed_milestone`, completion records and settlement/refund security tests. Shared escrow-helper interfaces require joint review.
3. In parallel, Harshita implements `assign_student`, `submit_milestone`, and `attest_milestone`, along with the GitHub automated verification service, verification authorization and replay protection, verification security tests, and the student and verification TypeScript client.
4. Harshita coordinates end-to-end integration. Palak and Harshita jointly verify cutoff boundaries, replay, failed CPI rollback, and cross-milestone fund isolation before any separately approved Devnet deployment. Give Ganga the reviewed IDL, transaction status model, and both TypeScript client interfaces.
5. Ganga owns the complete frontend, including the organization and student dashboards, internship opportunities, Proof Vault, and frontend UI testing and integration. Integrate against the reviewed interfaces.
